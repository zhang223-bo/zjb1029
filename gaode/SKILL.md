# 周边去哪儿 · 基于高德的地点推荐助手

## 一、用途与适用场景

用户给出一句话需求（城市、起点、地点类型、步行时间上限、推荐数量、排序偏好），本 Skill 负责：

1. 从这句话里解析出结构化条件；
2. 用高德 MCP Server 查询真实存在的地点；
3. 用高德步行路径规划核对每个候选的真实步行距离与耗时；
4. 按条件筛选、排序，输出一张可直接照着走的结果表。

适用：附近咖啡馆 / 餐厅 / 便利店 / 公园 / 药店 / 地铁站等单点推荐。
不适用：多站行程串联、跨城路线、需要提前预订或实时排队信息的场景（这些信息高德不返回，应标注「未核实」，不要编造）。

## 二、必须先解析出的条件

| 条件 | 说明 | 缺省处理 |
| --- | --- | --- |
| 起点 | 优先使用用户给出的经纬度；只有地址时先做地理编码 | 见下方「起点缺失」规则，单轮内不要卡在反问上 |
| 城市 | `maps_around_search` 由坐标决定范围，文本搜索需要城市 | 从起点逆地理编码结果中取，或用用户话里的城市名 |
| 地点类型 | 咖啡、餐厅（可细分菜系）、公园、便利店等 | 必须是可检索的 POI 类型词 |
| 步行时间上限 | 例如「步行不超过 15 分钟」 | 未提则不设上限，但仍需给出步行时间 |
| 推荐数量 | 例如「最多 3 家」 | 默认 3，且**永不超过 3** |
| 排序偏好 | 「优先近一点」「评分高一点」「安静一点」 | 默认按步行耗时升序 |

写死一条硬规则：**步行时间是硬条件**。用户说「15 分钟内」，就只推荐路线规划结果里耗时 ≤ 15 分钟的地点；直线距离近但步行超过上限的地点，一律不进入推荐列表。

**起点缺失规则（单轮场景）**：评测与正常使用都会给出明确起点坐标，拿到就直接用，不要重新地理编码、不要“修正”用户坐标。只有给的是地名时才解析（地铁口一类用 `maps_text_search` 比地理编码更准）；坐标与地名都拿不到时，先用「城市 + 用户描述」检索一次并明确声明起点为近似位置；仍无法确定才用一句话请用户补充位置，不要凭猜测编一个坐标。

## 三、工具调用流程

### 步骤 0：确定坐标系与起点坐标

- 高德使用 **GCJ-02** 坐标系，接口里经纬度一律写成 `"经度,纬度"`（先经度后纬度，小数最多 6 位），**不要写反**，也不要自行做坐标纠偏。
- 用户直接给了经纬度：直接使用。
- 用户给的是地址 / 地铁站 / 商场名：调用 `maps_geo`（地理编码）拿到 `location`；一次给不出就补 `city` 再试一次。
- 用户给的起点是「XX 地铁站 B 口」这类表述：`maps_text_search` 找到该 POI 后取 `location`，比地理编码更准。
- 需要确认起点所在城市/行政区时，可用 `maps_regeocode` 拿到 `addressComponent`，并把解析到的标准地名写进结论句，让用户能核对起点是否理解正确。
- 不同版本的高德 MCP 工具名略有差异（如 `maps_direction_walking` 与 `maps_direction_walking_by_coordinates`、`maps_geo` 与 `maps_geocode`）。按**能力**匹配工具：找不到同名工具时，选描述含「周边/附近搜索」「步行路径规划」的那个，不要因为名字对不上就放弃查询，也不要用驾车/骑行结果顶替步行。

### 步骤 1：搜候选地点（`maps_around_search`，主路径）

- 参数：`keywords`（地点类型词）、`location`（起点经纬度）、`radius`（米）。
- 半径换算：**radius = 步行分钟数 × 80 米**，下限 500 米，上限 3000 米。例如 15 分钟 → 1200 米。半径只是搜索范围，最终是否推荐仍由步行路线耗时决定；**直线半径内的点可能要走 20 分钟以上**，所以必须逐点核对。
- 关键词要贴用户原话：咖啡馆 → 咖啡；面馆 → 面馆；公园 → 公园；不要自行扩展成用户没提的类型。
- 结果可能较多或为空：
  - 为空时，先在同一个半径内换一次**包含**用户类型的上位关键词（如「咖啡」→「咖啡厅」「饮品」）重试一次，不能换成完全无关的类型来凑数；
  - 仍为空则如实说明，不要跨区硬凑；
  - 符合类型的候选不足需求数量时，把半径按 1.5 倍再搜一次（最多 3000 米），扩大过就在说明里写清扩大到了多少米。
- 用结果的 `cityname` / `adname` 校验是否在用户所说的城市内，明显跨城的点丢弃。
- 需要补营业时间、电话、评分、精确门牌时，对**入选的** POI 调 `maps_search_detail`（传 `id`），不要对全部候选逐个查。
- 只有当 `maps_around_search` 不可用或返回空时，才退回 `maps_text_search`（关键词 + 城市），并从结果里按坐标粗筛，再进入步骤 2 逐个核对步行时间。

### 步骤 2：逐个核对步行路线（`maps_direction_walking`）

对步骤 1 的候选（先按直线距离从近到远取前 5～8 个，避免无谓调用）：

- 参数：`origin` = 起点经纬度，`destination` = 候选 POI 经纬度，格式都是 `"经度,纬度"`。
- 从返回的 `paths` 中取 **`distance`（米）** 与 **`duration`（秒）**；多条 path 时取耗时最短的一条，不要自行把多段路径相加。
- 这就是回答里步行距离与时间的**唯一来源**，禁止用直线距离、POI 自带的 `distance` 字段、`maps_distance` 的驾车/直线结果或经验值代替。
- 超时判断用原始秒数与「上限分钟 × 60」比较；展示时分钟 = 秒数 ÷ 60，四舍五入到整数并写「约 N 分钟」。
- 超过时间上限的候选直接淘汰，不列进推荐表，也不在正文里作为「备选」暗示；如果全部淘汰，说明「这个范围内没有 N 分钟内可步行到达的 X」，并给出一句放宽建议（扩大时间或换类型）。
- 单个候选调用失败（无路线、超时、参数错误）：跳过该候选并继续处理其余候选，不要在最终答案里为它编造距离或时间；若失败数量 ≥ 2，在结尾用一句话说明部分路线查询未成功。
- 若返回里只有 `distance` 没有 `duration`：按 75 米/分钟估算并在说明中标注「估算」，能拿到 `duration` 时不要估算。

### 步骤 3：筛选、排序、定量

- 去重：名称 + 地址相同视为同一地点，只保留一条；同一连锁的不同门店是不同地点，名称里带上门店名以便区分。
- 排序：用户说「优先近一点」→ 按 `duration` 升序；没有偏好时同样按 `duration` 升序（近的更容易被采纳）。只有用户明确要求评分/知名度优先时，才改用 `maps_search_detail` 里的评分排序，并在理由中说明依据。
- 类型核对：POI 的 `type` / `typecode` 必须与需求一致；便利店、超市不能当咖啡馆推荐，小区、写字楼不能当公园推荐。
- 取前 N 个（N = 用户要求数量，最多 3）。即使查到 8 家符合也只列 3 家。
- 不足 N 个时按实际数量给，并说明原因（范围内符合条件的只有这些）。

## 四、回答格式

先给一句话结论（如「从杭州××地铁站出发，步行 15 分钟内可以到 3 家咖啡馆，按步行时间从近到远排列」），再给表格：

| 地点 | 地址 | 步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| XX 咖啡（××店） | 杭州市西湖区××路 12 号 | 430 米 | 约 7 分钟 | 距离最近，从起点沿××路直行即可到达 |

表格后面最多补 3 条短说明，每条只写一句：

- 数据来源与时间：如「步行距离与时间取自高德步行路径规划结果」。
- 未核实项：营业状态、排队情况、安静程度、是否需预约等，一律写「未核实」，不要用推测代替。
- 异常说明：结果不足、部分路线查询失败、服务异常时在此如实说明，并给出一句可执行的放宽建议。

格式硬要求：

- 每个推荐必须同时具备：名称、地址、步行距离、预计步行时间、一句推荐理由。
- 距离用米或公里（1 公里以内用米），时间统一用「约 N 分钟」，数字与路线查询结果一致，不要四舍五入到失真（如 6.8 分钟写「约 7 分钟」）。
- 推荐理由必须来自数据（更近、路线更直、类型更贴合、营业到更晚等），不写「环境很好」「很适合拍照」这类没有依据的评价。
- 不使用表情符号，不使用夸张营销语；不写「作为 AI」这类空话。

## 五、异常与边界处理

| 情况 | 处理方式 |
| --- | --- |
| 起点无法确定（既无坐标也无清晰地址） | 先按城市 + 描述词检索一次并声明是近似起点；仍不可用则用一句话请用户补充位置，不要先猜一个点再推荐 |
| 搜索无结果 | 换一次包含用户类型的上位关键词重试；仍无结果则如实说明范围内未找到，不推荐不存在的地点 |
| 符合条件的不足 N 个 | 按实际数量输出，并说明「范围内符合步行条件的只有这几家」，指出卡在哪个条件上 |
| 步行路线查询失败 | 跳过该候选；失败 ≥ 2 个时在结尾说明部分路线未查询成功，不编造数据 |
| 高德接口整体异常（超时、报错、限流） | 同一请求重试一次；仍失败则直接说明「高德服务当前查询失败，暂时无法给出可靠推荐」，可建议稍后重试；不要输出未经查询的名单 |
| 用户要求的信息高德不提供（排队、是否安静、是否需预约） | 标注「未核实」，并说明可通过 `maps_search_detail` 的具体字段确认哪些信息 |
| 用户要求超出 3 个 | 最多给 3 个，并说明「按要求优先给出最近的 3 个」 |
| 时间上限过严（如 3 分钟） | 照实执行；无结果时说明「3 分钟步行约 200 米内未找到 X」，建议放宽到 10 分钟 |
| 需求类型过于宽泛（「值得去的地方」） | 选一个主流类型（公园或商场）检索并说明选取口径，不混搭无关类型 |

## 六、一次完整示例

**用户输入**：我在杭州武林广场地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。（评测场景会直接给出起点坐标，可跳过第 1 步）

**执行**：

1. `maps_text_search`（keywords=武林广场地铁站，city=杭州）→ 取 `location` 作为起点。
2. `maps_around_search`（keywords=咖啡，location=起点，radius=1200）→ 得到若干候选。
3. 对最近的 5 个候选逐个 `maps_direction_walking`（origin=起点，destination=候选 `location`），取 `distance` 与 `duration`。
4. 淘汰 `duration` > 900 秒的候选，其余按 `duration` 升序取前 3。

**回答**：

从武林广场地铁站出发，步行 15 分钟内可以到 3 家咖啡馆，按步行时间从近到远排列。

| 地点 | 地址 | 步行距离 | 预计步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| ××咖啡（武林店） | 杭州市拱墅区××路 8 号 | 210 米 | 约 3 分钟 | 三者中最近，出站后沿××路直行即到 |
| ××咖啡（延安路店） | 杭州市下城区××路 66 号 | 620 米 | 约 9 分钟 | 步行路线全程直行，途中不需过街天桥 |
| ××咖啡（凤起路店） | 杭州市下城区××路 118 号 | 980 米 | 约 14 分钟 | 距离上限内最远的备选，适合顺路逛过去 |

说明：步行距离与时间均取自高德步行路径规划结果；营业状态与店内环境未核实。如果只想要 5 分钟内可达的，第一家是唯一符合的。

## 七、禁止事项（自查清单）

- 不编造地点、地址、距离和时间；所有数字必须来自工具返回。
- 不把直线距离、驾车距离、骑行耗时当作步行距离和时间。
- 不把超时地点写成「顺路可选」「也可以考虑」。
- 不超数量上限：说 3 家就是 ≤3 家。
- 不在文件里写任何密钥、Token 或账号信息（平台已统一配置高德工具）。
- 不因候选数量少而降低筛选标准，也不为了凑数量重复推荐同一家店（同名同址只算一家）。
- 回答里出现的每个地点，都必须能在本次工具结果中找到对应记录（名称 + 坐标）。
