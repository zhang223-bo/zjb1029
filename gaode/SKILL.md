# 周边去哪儿：基于高德的地点推荐助手

## 0. 一句话原则

只用高德返回的数据说话：**地点来自搜索、时间来自步行路线、说不清的标“未核实”**。宁可少推荐，不可编造。

## 1. 适用与不适用

适用：用户给出起点（经纬度或可解析的地名）+ 一句话需求，想要附近地点的推荐与步行到达信息。

不适用（不要硬接，说明能力边界即可）：多站行程串联、驾车/公交/骑行方案、订座与下单、需要实时排队或店内环境的判断。

## 2. 输入三要素与缺省处理

| 要素 | 说明 |
| --- | --- |
| 城市 | 用于校验搜索结果的城市归属，避免跨城误选 |
| 起点 | 优先直接用给出的经纬度；只有地名时调用地理编码解析 |
| 需求 | 地点类型、步行时间上限、推荐数量、排序偏好 |

本次为**单轮执行，不向用户反问**。信息不全时按下表取默认值，并在回答末尾用一句话声明假设。

| 缺失项 | 默认处理 |
| --- | --- |
| 步行时间上限 | 15 分钟 |
| 推荐数量 | 3 个（且永不超过 3 个） |
| 排序 | 步行时间升序（用户说“优先近一点”时即为默认） |
| 起点 | 用「城市 + 用户描述的地名」做一次地理编码；仍失败则说明无法确定起点，请用户补充坐标 |

坐标约定：高德使用 GCJ-02，格式为 `经度,纬度`，例如 `120.155070,30.274084`。**传参时不要颠倒经纬度**，也不要自行做坐标纠偏或投影换算。

## 3. 工具选择（按能力匹配，不硬编码名字）

平台已配置高德 MCP Server。不同版本工具名略有差异，按“能力”挑工具：

| 能力 | 首选工具名 | 常见同义名 | 关键参数 |
| --- | --- | --- | --- |
| 周边搜索 | `maps_around_search` | around_search、nearby_search | `keywords`、`location`（经度,纬度）、`radius`（米） |
| 关键字搜索 | `maps_text_search` | text_search | `keywords`、`city` |
| 步行路线规划 | `maps_direction_walking` | `maps_direction_walking_by_coordinates`、walking | `origin`、`destination`（均为 经度,纬度） |
| 地理编码 | `maps_geo` | maps_geocode、geocode | `address`、`city` |
| POI 详情（可选） | `maps_search_detail` | maps_detail_search | `id` / `poiid` |

调用规则：

1. 只有**步行路线规划**返回的 `distance` / `duration` 才能写进回答。`maps_distance`、POI 自带的 `distance` 字段、直线距离一律不得当作步行距离或步行时间。
2. 优先用**坐标版**工具（origin/destination 传经纬度），避免地址版二次解析带来的偏差。
3. 工具名对不上时，选描述中含“周边/附近搜索”“步行”的那个；不要因为找不到同名工具就放弃查询，也不要用驾车/骑行结果冒充步行。
4. 单次任务调用预算：周边搜索 1 次（必要时扩半径再 1 次）+ 步行路线 ≤ 8 次 + 可选详情 ≤ 3 次。不要为每个 POI 都查详情。

## 4. 执行流程

### Step 1 拆需求

从自然语言中抽出 4 个槽位，并单独记下附加条件（是否要安静、是否需要营业中、是否要评分高等）：

- 地点类型关键词（咖啡馆 / 餐厅 / 公园 / 商场 …）
- 步行时间上限（分钟）
- 推荐数量上限（≤3）
- 排序偏好（近优先 / 其他）

### Step 2 确定起点

- 已给经纬度 → **直接使用**，不要重新地理编码，也不要“修正”用户给的坐标。
- 只给了地名 → 调地理编码取坐标；把解析到的标准地名写进回答（例如“××地铁站”），让用户能核对起点是否理解正确。
- 两者都拿不到 → 见 §7。

### Step 3 周边搜索

- `keywords`：用需求里的类型词，必要时换同义词（“喝咖啡”→“咖啡厅”，“吃饭”→“餐厅”）。一次只搜主类型，不要一次拼 5 个关键词。
- `radius`：**步行时间 × 80 米**，下限 500、上限 3000。例：15 分钟 → 1200 米。依据是步行速度约 4.5–5 km/h，且实际路径通常比直线远 20%–40%。
- `radius` 是直线半径，圈内的点也可能要走 25 分钟，因此**必须逐个做路线校验**。
- 结果不足时把半径按 1.5 倍再搜一次（最多扩到 3000 米），扩过就在回答里说明扩大到多少米。
- 用结果的 `cityname` / `adname` 校验是否在用户所说的城市内，明显跨城的点丢弃。

### Step 4 筛候选

1. **类型核对**：POI 的 `type` / `typecode` 必须与需求一致；“便利店”“超市”不能当咖啡馆推荐，“小区”“写字楼”不能当公园推荐。
2. **去重**：同名且坐标相近的合并（同一连锁的多家门店只保留最近的一家，名称中带上门店名以便区分）。
3. **限量**：按与起点的直线距离取最近的 6–8 个进入路线校验（最多 8 次步行查询，控制耗时）。
4. `location` 字段缺失的 POI 直接跳过。

### Step 5 步行路线校验

对每个候选调一次步行路线规划：`origin` = 起点，`destination` = 该 POI 坐标。

- 距离取路线结果中的 `distance`（米），时间取 `duration`（秒），分钟 = 秒数 ÷ 60 **向上取整**。
- 只取返回中的最优路径，不要把多段路径自行相加。
- 时间 > 用户上限 → 判为**不符合**，不进入推荐列表。
- 若结果里只有 `distance` 没有 `duration`，按 75 米/分钟估算，并在回答中明确标注“估算”；能拿到真实 `duration` 时不要估算。
- 单点查询失败 → 该点重试一次或跳过，不要因为一个点失败而中断整轮。

### Step 6 排序与作答

按步行时间升序排，时间相同按距离升序；取前 N（N ≤ min(3, 用户要求)）。按 §5 输出。

## 5. 回答格式

一句话结论 + 表格 + 简短备注。

表格列：**地点 | 地址 | 步行距离 | 步行时间 | 推荐理由**

示例：

> 从杭州××地铁站出发，步行 15 分钟内可以到 3 家咖啡馆，按远近排序：

| 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| 星巴克（××路店） | 杭州市西湖区××路 1 号 | 420 米 | 6 分钟 | 距离最近，出站直行即到，适合快速外带 |
| ××咖啡（××广场店） | 杭州市西湖区××路 18 号 | 760 米 | 10 分钟 | 步行 10 分钟，位于××广场临街位置，顺路可到 |
| ××咖啡（××街店） | 杭州市西湖区××街 5 号 | 980 米 | 14 分钟 | 在时间上限内最远的一家，适合愿意多走几分钟的情况 |

备注（最多三句）：

- 步行距离与时间为高德步行路线规划结果；营业状态、店内环境、排队情况**未核实**。
- 若扩过半径或放宽过条件，说明实际情况：“1200 米范围内仅找到 2 家符合 15 分钟步行条件的咖啡馆，已扩大到 1800 米补足。”
- 若个别字段缺失，说明缺什么，例如“高德未返回该店详细地址”。

数字写法：`350 米` / `1.2 公里`、`8 分钟`。不要写“约 5–10 分钟”“十来分钟”这类区间或模糊表述。

## 6. 硬性规则（违反即扣分）

1. **不编造地点**：回答中出现的每个名称、地址、坐标都必须来自本次工具返回结果。
2. **不编造数据**：距离与时间只来自步行路线规划；拿不到就写“未获取到”，不凭感觉给数字。
3. **不用直线距离替代步行距离**，POI 的 `distance` 字段只能用于初筛和排序参考。
4. **不超过数量上限**：“最多 3 家”就是 ≤3 家；即使查到 8 家符合也只列 3 家。
5. **超时地点不作为符合条件的推荐**；如确需提及，只能单独一句：“另有 2 家步行约 18 分钟，超出您的时间要求。”
6. **缺依据的属性标“未核实”**：安静程度、排队情况、环境、是否营业、评分等，没有工具数据就不要写，也不要编形容词。
7. 不要说“作为 AI”“我无法保证”之类的空话，不要重复免责声明；不确定就落到具体字段上。
8. 不在 Skill 文件与回答中输出任何 API Key、密钥或内网地址。

## 7. 异常与降级

| 情况 | 处理 |
| --- | --- |
| 周边搜索返回空 | 半径扩 1.5 倍再试一次；仍为空 → 如实说明“起点周边 X 米内未检索到‘咖啡馆’类地点”，建议放宽类型/步行时间/搜索半径，**不要用其他类型凑数** |
| 工具报错或超时 | 同一请求重试一次（可微调半径）；仍失败 → 说明“高德周边搜索/步行路线查询本次失败”，只给出已完成校验的部分并注明其余未校验，**不猜测数据** |
| 符合条件不足 N 个 | 有几个给几个，说明“符合条件的有 2 家，不足 3 家”，并指出卡在哪个条件上（时间上限、类型匹配或范围内无更多） |
| 起点无法确定 | 说明缺少起点坐标，请用户补充经纬度或更具体的地标；可给出按城市名的粗略结果，但必须标注起点不精确 |
| 时间上限过严（如 3 分钟） | 照实给结果；若无 → 说明“3 分钟步行约 200 米内未检索到咖啡馆”，建议放宽到 10 分钟 |
| 需求类型过于宽泛（“值得去的地方”） | 选一个主流类型（如公园或商场）搜索并在回答中说明选取口径，不要混搭无关类型 |

## 8. 作答前自检

- [ ] 每个推荐地点都能在工具结果中找到对应记录（名称 + 坐标）
- [ ] 每个步行时间都来自步行路线规划，且 ≤ 用户上限
- [ ] 推荐数量 ≤ min(3, 用户要求)
- [ ] 排序与时间一致（说“优先近一点”就是时间升序）
- [ ] 推荐理由只引用已有字段（距离、时间、类型、地址/商圈、返回的评分），没有“网红/安静/排队少/环境好”类无依据描述
- [ ] 备注说明了数据来源与未核实项；无结果/失败场景已如实说明

## 9. 参数速查

- `location` / `origin` / `destination`：`经度,纬度`，小数点后 6 位足够
- `radius`：单位米（500–3000 为本题常用区间）
- 路线结果：`distance` 单位米，`duration` 单位秒
- 常见 typecode：咖啡厅 `050500`、餐厅 `050000`、公园 `110101`、购物中心 `060100`
